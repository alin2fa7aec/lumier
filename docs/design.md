# lumier — 設計方針

NAS 上の画像を、フォルダのグラフ構造を「美術館の部屋」に見立ててブラウザから閲覧するビューワ。

このファイルは**設計の根拠**を記録する。進捗・未決事項・次にやることは `.local/status.md`。

## 1. 確定した選択

| 項目 | 選択 | 理由 |
|---|---|---|
| 体験 | 2D 横スクロールの壁（多段吊り）、左右端に扉 | ウォークスルーを廃し、スクロールだけで鑑賞。実装が軽く、スマホでも快適 |
| 配信 | axum サーバ + ブラウザ | PC でもスマホでも見られる。NAS 隣接機に単一バイナリで置ける |
| バックエンド | Rust (axum + tower-http) | `ServeDir`/`ServeFile` が Range・ETag・条件付き GET を標準で処理する |
| フロント | TypeScript + React (Vite) | DOM/CSS の横スクロールと遅延読み込みをそのまま使える |
| グラフ定義 | ルート直下の `museum.yaml` 1 枚 | 全体を一望でき、git 管理・手編集・差分レビューが容易。NAS 側を汚さない |
| 対象 | 写真（縦長・HEIC を含む）、動画、PDF、Markdown | 2026-10-11 に見直し。一覧にサムネイルを並べ、選んだら本体を閲覧できるところまで（§6.6）。Markdown は 10-12 に追加（§6.8） |

### 見送った選択: Immich をバックエンドにする

走査の永続化、再走査、認証、HEIC、動画のトランスコードを Immich に任せ、lumier を見せ方だけの
フロントにする案を検討して見送った。理由は 3 つ。

- **PDF を扱えない。** Immich が取り込むのは写真と動画だけなので、PDF のために走査・サムネイル・
  キャッシュを結局自前でも持つ二本立てになり、任せる利点の大半が消える。
- **壁は Immich を使っても自前。** 縦横混在の詰め方（§6.5）は Immich の縦スクロールのグリッドでは解決しない。
- **構成が重くなる。** Postgres・Redis・機械学習コンテナを含む一式になり、「NAS 隣接機に単一バイナリ」が崩れる。

Immich に分があるのは動画のトランスコードだけで、それは今の範囲外（§8）。

### 前提にした判断（要確認）

- **バックエンドは常に「ただのファイルシステムパス」を見る。** アプリ内 SMB クライアントは使わない。
  これによって **PoC のローカルディレクトリと本番でコードパスが完全に同一**になり、PoC が捨て実装にならない。
- **lumier は NAS 本体で動かす（2026-10-11 に変更）。** 当初は別の機械から CIFS マウント越しに読む前提だったが、
  NAS は自前の Linux サーバ（NixOS）にすると決まったので、同じ機械でローカルディスクを直接読む。
  SMB は PC からの整理とスマホからのアップロードのための口で、lumier の読み取り経路には入らない（§6.7）。
- **段階4までの対応形式は JPEG / PNG / WebP / GIF のみ。** HEIC・RAW は `image` crate 単体では読めず `libheif` 等の C ライブラリが必要なので、PoC では意図的に範囲外に切った。
  本番の対象に HEIC・動画・PDF が含まれると分かったので、段階5で足す（§6.6）。RAW は範囲外のまま。
- **縦方向は多段吊り。** 当初は 1 段（横一列）としていたが、段階4 のあとに変更した。「天井はなく」は
  部屋の枠（天井・床・壁面装飾）を描かないという意味に留め、縦方向はグリッドとして使う。
  **列優先**（上から下に詰めて右へ続く）なので、**スクロールは依然として横方向だけ**であり、
  扉・スクロール位置の復元・キーボード操作はそのまま成立する。段数はビューポートから決まる（§6.5）。

## 2. 体験のモデル

### 部屋 = 1 本の横長の壁

```
  ┌──────────────────────────────────────────────────────────────┐
  │ ╔════════╗ ┌────┐┌──────┐┌───┐┌─────┐┌────┐┌───┐  ╔════════╗ │
  │ ║ 扉     ║ │ 1  ││  5   ││ 8 ││ 11  ││ 14 ││17 │  ║ 扉     ║ │
  │ ║エント  ║ └────┘└──────┘└───┘└─────┘└────┘└───┘  ║夜景の間║ │
  │ ║ランス  ║ ┌──────┐┌───┐┌────┐┌───┐┌─────┐┌────┐  ║        ║ │
  │ ║        ║ │  2   ││ 6 ││ 9  ││12 ││ 15  ││ 18 │  ║ 扉     ║ │
  │ ║        ║ └──────┘└───┘└────┘└───┘└─────┘└────┘  ║海の間  ║ │
  │ ║        ║ ┌───┐┌────┐┌──────┐┌────┐┌───┐┌─────┐  ║        ║ │
  │ ║        ║ │ 3 ││ 7  ││  10  ││ 13 ││16 ││ 19  │  ║        ║ │
  │ ╚════════╝ └───┘└────┘└──────┘└────┘└───┘└─────┘  ╚════════╝ │
  └──────────────────────────────────────────────────────────────┘
    ↑ scroll 開始端                               scroll 終了端 ↑
```

**列優先**に詰める（上から下、それから右へ）。1 列が壁の高さに収まるので縦にはあふれず、
**スクロールは横方向のみ**。端まで行くとそれ以上スクロールできない（ラップもバウンドもしない）。

### 扉は「端の扉群」であり、1 つに限らない

左右の端が**それぞれ複数の扉を持てる**ことで、2D 横スクロールの単純さを保ったまま一般のグラフを表現できる。
ハブ部屋の右端に扉を 5 つ並べれば分岐になり、一直線の並びにすれば回廊になる。

扉は行き先の部屋名と進む向きの矢印だけを、端の縦中央に文字で出す。扉の形には描かず、ホバー時の動きも付けない。当初は行き先の1枚目のサムネイルを覗き見として出していたが、主役は壁の絵なので案内は目立たないほうがよいと考え、2026-11-21 に外した。API は今も `peek` を返しているので、覗き見を戻すときはフロントエンドだけで済む。

### 移動したときのスポーン位置（連続性の規則）

- **右の扉から入ったら、次の部屋の左端に出る**
- **左の扉から入ったら、次の部屋の右端に出る**

進行方向が保たれるので「歩いている」感覚が出る。加えて、各部屋のスクロール位置を `sessionStorage` に部屋 ID ごとに保存し、
扉を通って戻ってきたときは元の位置に戻す。これがないと館内を往復するたびに端に飛ばされて体験が崩れる。

### 見取り図は移動手段である（段階4）

当初これを「現在地の把握」のための館内マップとして書いていたが、`ss/` を一本道の回廊として組んでみて
前提が変わった。**20室の鎖では端の部屋まで扉を20回通ることになる**。扉だけが移動手段だと、
グラフが深くなるほど遠い部屋が実質的に到達不能になる。

したがって見取り図は補助ではなく**第二の移動手段**として設計する。

- どの部屋へも1手で飛べる（グラフを辿る必要がない）
- 現在地と、そこから扉で繋がっている部屋が区別して見える
- 飛んで入った場合のスポーン位置は左端（進行方向の継承が成り立たないため）

**実装（段階4）**: グラフを描画する代わりに、**エントランスからの手数で列に分けて横スクロール**する形にした。
回廊は「1室ずつの列が長く並ぶ」、ハブは「1列が高くなる」という形で構造がそのまま見える。
グラフ配置アルゴリズムを持たずに済み、しかも操作がアプリの他の部分（横スクロール）と揃う。

副産物として、この列表示が `ss/` の問題をそのまま可視化した — `ac_valhalla` は**エントランスから21手**。
設計の「遠い部屋を作りすぎない」という注意がそのまま当てはまる状態になっている。

**スポーン位置を「左端」から変更した。** 飛んだ先に保存済みのスクロール位置があればそれを復元し、
無いときだけ左端にする。設計で左端と書いた理由は「進行方向が継承できない」ことだったが、
位置の復元は別の機構であり、復元できるならそちらが望ましい。整理すると:

| 入り方 | スポーン位置 |
|---|---|
| 右の扉を通った | 次の部屋の左端 |
| 左の扉を通った | 次の部屋の右端 |
| 見取り図から飛んだ | 保存位置、無ければ左端 |
| ブラウザの戻る/進む、再読込 | 保存位置、無ければ左端 |

扉の場合に復元ではなく端にするのは、**扉はその端にあるから**。歩いて入れば扉の位置に立つのが自然で、
実際には扉に辿り着くためにその端まで歩いているので、復元と一致することが多い。
戻る/進むで方向規則を再適用しないよう、入り方は history state には持たせていない。

### 操作

| 入力 | 動作 |
|---|---|

| ← → | スクロール |
| Home / End | 左端・右端の壁まで |
| 作品クリック | ライトボックス。画像は拡大表示、動画は再生、PDF は本体を開く（§6.6） |
| 扉クリック / 端で Enter | 隣の部屋へ |

| 壁の選択モードでタップ | 削除予定の印を付け外す (段階9, §6.9) |

### スライドショー

館全体を1本の順路として流す。順路はエントランスから扉をたどる深さ優先で、右の扉を左の扉より先に、端の中では manifest に書いた順に入る。扉の並べ方がそのまま見せる順番の指定になるので、順路のための設定を別に持たずに済む。扉で辿り着けない部屋は、最後に manifest の順で足す。空の部屋は飛ばし、最後まで行ったら頭に戻る。

1枚あたりの時間は30秒, 1分, 2分, 4分, 8分, 16分からドロップダウンで選び、既定は30秒。1分から倍々にしているのは、フォトフレームでは一目見る程度から長く掛けておくまでを少ない選択肢で覆いたいから。選んだ値は `localStorage` に残す。壁の位置のようにタブごとではないのは、どの速さがよいかは映している画面で決まり、フォトフレームなら置いたときの速さで再開してほしいから。切り替えはクロスフェード。次の画像はデコードを終えてから差し替えるので、読み込み途中の画像にフェードすることはない。画像は `orig` ではなく画面の長辺を満たす最小のサムネイルを使う。ライトボックスで `orig` を出すのは見たい1枚を選んだからで、自動で流れ続ける表示に元ファイルの重さは見合わない。

背景は不透明にし、キャプションと操作は2.5秒触らなければ隠す。止めたときは、流れた先の部屋に移ってそこで終える。始めた部屋に戻すと、見ていた写真を見失うため。

全画面表示と、画面のスリープを止める Wake Lock は、フォトフレームとして据え置くなら要る (§8)。

## 3. `museum.yaml` 仕様

扉は 2 部屋の間の関係なので、部屋ごとに書くのではなく**辺のリスト**として独立させる。
「A は B に繋がっていると書いたのに B 側が繋がっていない」という不整合が構造的に起きなくなる。

```yaml
version: 1
entrance: lobby

rooms:
  - id: lobby
    name: エントランス
    # path 省略可 — 画像のない通路・ホールとして使える

  - id: landscape
    name: 風景の間
    path: photos/landscape
    order: name          # name | mtime | taken (既定: name、自然順ソート)

  - id: night
    name: 夜景の間
    path: photos/night

  - id: sea
    name: 海の間
    path: photos/sea

doors:
  - { from: lobby,     to: landscape, side: right, label: 風景の間へ, reciprocal: true }
  - { from: landscape, to: night,     side: right, reciprocal: true }
  - { from: landscape, to: sea,       side: right, reciprocal: true }
```

- `side` は **`from` 側の壁のどちら端に扉を置くか**。
- `reciprocal: true` で `to` 側の反対端に戻り扉を自動生成する（既定 `true`）。
- `path` はルート相対。ルート外に出るパスは起動時に拒否する。

### `lumier check` で検証する内容

エラーとして落とすもの:
- `id` の重複、`[a-z0-9_-]+` に合わない `id`
- `path` が存在しない / ディレクトリでない / 正規化後にルート外に出る
- `doors` の `from`/`to` が存在しない部屋を指している
- `entrance` が存在しない部屋を指している

警告として報告するもの:
- `entrance` から到達できない部屋
- どの部屋にも割り当てられていないルート配下のフォルダ（取りこぼしの検出）
- 同じ `path` を指す複数の部屋

この検証を**サーバ起動時にも必ず通す**。壊れたマニフェストで起動して実行時に初めて気づく、という状態を作らない。

## 4. システム構成

```
lumier/
├─ crates/
│  ├─ museum-core/      マニフェスト解析・検証、部屋グラフ、ライブラリ走査、
│  │                    画像メタデータ、サムネイル生成パイプライン
│  └─ museum-server/    axum: HTTP API、SPA 配信、サムネイルキャッシュ、CLI
└─ web/                 Vite + React + TypeScript
```

PoC の段階から `museum-core` を切り出す理由は 2 つ。`lumier check` を CLI として単体で走らせたいこと、
そして将来 Tauri / Slint のネイティブ版を足す余地を、今ほとんどコストをかけずに残せること。

### 起動

```
lumier serve --root /mnt/nas/photos \
              --manifest museum.yaml \
              --cache-dir ~/.cache/lumier \
              --bind 127.0.0.1:8080
```

`--manifest` はルート相対（既定 `museum.yaml`）。

## 5. API 設計

```
GET /api/museum            館内マップ用。部屋一覧と扉一覧（画像は含まない）
GET /api/rooms/{room_id}   部屋の中身。画像リスト（寸法つき）と左右の扉
POST /api/rescan           マニフェストを読み直してライブラリを再走査する (§6.2)
GET /img/{image_id}/{size} 画像バイト。size = 320|640|1280|2560|orig（長辺基準）
GET /*                     SPA フォールバック
```

段階9で、削除予定と trash を扱う API を足す (§6.9)。

### 設計上の要点: **API はファイルシステムパスを一切受け取らない**

画像は不透明な ID（`blake3(ルート相対パス)` の先頭 16 バイトを hex 化）で指す。走査時に `id → 相対パス` の索引を
メモリに持ち、リクエストはこの索引を引くだけ。URL にパス片が現れないので、**パストラバーサルが攻撃面として
そもそも存在しなくなる**。入力検証の抜け漏れに頼る設計を避ける。

### `GET /api/rooms/{room_id}` のレスポンス

```json
{
  "id": "landscape",
  "name": "風景の間",
  "images": [
    { "id": "a3f1...", "name": "IMG_0021.jpg", "w": 4032, "h": 3024, "v": "8c2e" }
  ],
  "doors": {
    "left":  [{ "to": "lobby", "name": "エントランス", "peek": "b7d2..." }],
    "right": [{ "to": "night", "name": "夜景の間",   "peek": "e109..." },
              { "to": "sea",   "name": "海の間",     "peek": "4ab8..." }]
  }
}
```

**`w` / `h` を必ず返すことが、この API のいちばん重要な点。** 寸法が分かっていれば、フロントは
1 枚もピクセルが届く前に壁の最終レイアウトを確定できる。これがないと画像が読み込まれる順に幅が決まって
スクロール位置が飛び、横スクロールの体験が壊れる。寸法は走査時にヘッダだけ読んで取得する（全体のデコードは不要）。

### キャッシュ

`v` は `(mtime, ファイルサイズ)` の短縮ハッシュ。画像 URL は `/img/{id}/{size}?v={v}` の形で、

```
Cache-Control: public, max-age=31536000, immutable
```

を付ける。ID は安定（= 恒久的に同じ画像を指す）なので長期キャッシュが効き、ファイルが差し替わったときは
部屋 API が返す `v` が変わって URL ごと変わるため確実に無効化される。ID だけで `immutable` を付けると
差し替え後も永久に古い画像が出続けるので、この `v` は省略できない。

### 種別（段階5で追加）

`images` の各要素に `kind`（`image` | `video` | `pdf`）を足す。動画には `duration`（秒）も付ける。
`w` / `h` はどの種別でも**壁に掛かる絵の表示寸法**で、動画は回転を適用したあとの寸法、PDF は 1 ページ目の寸法。
これでフロントのレイアウトは種別を知らずに済む。

エンドポイントは増やさない。`/img/{id}/{size}` の数値サイズはどの種別でも WebP のサムネイルを返し、
`orig` は元ファイル（HEIC、動画、PDF）をそのまま返す。パス名の `img` と配列名の `images` は
実態より狭い名前になるが、変えるのは見た目だけの変更なので据え置く。

## 6. 技術的な難所と対策

ここが実装前に詰めておく価値のある部分。

### 6.1 サムネイル生成 — 性能の本番

2000 枚のフォルダで原寸を配ることはできない。生成パイプラインには 4 つの独立した落とし穴がある。

1. **サイズは固定の離散集合にする。** 長辺 320 / 640 / 1280 / 2560。`?w=` で任意幅を受けると
   キャッシュが無限に散り、`srcset` も書けない。
2. **ディスクキャッシュを掘る。** `{cache}/{size}/{id[0:2]}/{id}.webp`。先頭 2 文字でシャーディングして
   1 ディレクトリに数万ファイルが入る状態を避ける。PoC では追い出しなし、LRU は後回し。
3. **同一キーの同時生成を 1 回に畳む（single-flight）。** 未生成のサムネイルに 50 本同時にリクエストが来ると、
   素朴な実装では 50 回デコードする。キーごとの待ち合わせ（`DashMap<Key, broadcast::Sender>` 等）が必要。
4. **CPU を明示的に絞る。** デコードとリサイズはブロッキング CPU 作業なので `spawn_blocking` に出し、
   **さらにコア数程度のセマフォで同時実行数を制限する**。これを忘れると 200 本の同時リクエストが
   blocking スレッドプールを食い尽くし、API も静的ファイルも含めてサーバ全体が止まる。

**EXIF Orientation を必ず適用する。** `image` crate は自動で向きを直さない。`kamadak-exif` で
Orientation タグを読んで回転・反転を掛ける。これを落とすとスマホで撮った写真が横倒しで並ぶ。

> **段階分けの誤り（段階2で判明）**: Orientation はサムネイル（段階3）の話として書いていたが、
> **段階2に前倒しが必要だった**。ブラウザは `<img>` の描画時に EXIF Orientation を既定で適用するため、
> 四半回転した写真は表示上の縦横が入れ替わる。API が記録上の寸法をそのまま返すと壁が誤った形に組まれる。
> `probe` は Orientation 5〜8 のとき `w`/`h` を入れ替えて返す。

採用クレート: `image`（デコード）、`fast_image_resize`（SIMD リサイズ）、`kamadak-exif`（向き）、
**`webp`（libwebp バインディング、非可逆エンコード）**。`image` の WebP は可逆のみなので予想通り別クレートが必要だった。
`cc`/`cmake` があればビルドは通る。AVIF はエンコードが遅いので将来の選択肢。

**実測（段階3、`ss/myst` 32枚、2560x1440 の PNG 中心）**

| | 原寸 PNG | 2560 WebP | 1280 WebP | 640 WebP | 320 WebP |
|---|---|---|---|---|---|
| 1枚 | 2119 KiB | 172 KiB | 83 KiB | 37 KiB | 13 KiB |

壁ごとの転送量（32枚、ビューポート別に最小の rendition を選択）:

| ビューポート | frame 高 | 選択 | 転送量 | 段階2 比 |
|---|---|---|---|---|
| 2560x1440 | 1037px | 2560×31, 1280×1 | **2.98 MiB** | 1/28 |
| 1920x1080 | 778px | 2560×31, 1280×1 | **2.98 MiB** | 1/28 |
| 1536x864 | 622px | 1280×31, 640×1 | **1.47 MiB** | 1/56 |
| 390x844 dpr2 | 281px | 1280×31, 640×1 | **1.47 MiB** | 1/56 |

（段階2 では同じ壁が 82 MiB だった）

**3 つの防御が実際に効いていることの確認**

- **single-flight**: 未生成の 1 枚に 50 本同時 → **render は 1 回のみ**（97 ms）、50 本すべてに同一バイト列。
  これが無ければ 50 回デコードしていた
- **セマフォ**: 冷キャッシュで 149 枚を一斉要求（5.2 秒、14.3 MiB 生成）している最中の
  `/api/museum` が**中央値 2 ms・最大 77 ms**。API が詰まらない
- **原子的な書き込み**: 一斉生成後に `.part` の残骸 0 件

### 設計から変えた点（段階3）

**1. キャッシュパスに version を含める。** 設計では `{cache}/{size}/{id[0:2]}/{id}.webp` だったが、
`{id}-{v}.webp` にした。元ファイルが差し替わったとき、ID だけのパスでは古いサムネイルが
永久に返り続ける。古いエントリは追い出しまで残るが、それは LRU の仕事。

**2. `srcset` + `sizes` ではなく JS で rendition を選ぶ。**
`sizes` は**幅しか記述できない**。この壁のレイアウトは高さ駆動（`--frame-height`）で、
各画像の描画幅は「frame 高 × 画像のアスペクト比」から決まるため、`sizes` では表現できない。
よって `pickRendition(image, frameHeight, dpr)` で最小の rendition を選び `src` に入れる。
frame 高は CSS（`--frame-height`）が唯一の真実とし、JS は隠しプローブ要素を measure する
（`getComputedStyle` はカスタムプロパティを未評価のトークン列で返すため読めない）。

### 6.2 走査 — ローカルと CIFS で 2 桁変わる

> **前提の変更（2026-10-11）**: lumier を NAS 本体で動かすことにしたので、本番でも CIFS 越しには読まない。
> この節の CIFS に関する見積もりは、別の機械から読む構成に戻す場合の記録として残す。
> 永続化と明示的な再走査は引き続き必要（動画と PDF の走査が重く、アップロードでファイルが増えるため）。
> 並列化と `canonicalize` の削減は、ローカルディスクで実測して遅い場合だけ手を付ける。

**CIFS マウントの走査は遅い。** 1 ファイルごとの `stat` がネットワーク往復になるため、
ローカルで一瞬だったものが NAS では数分かかる。ここは PoC が嘘をつく箇所なので、最初から次の形にしておく。

- 走査は起動時に 1 回、結果をメモリに常駐
- 走査結果をディスクに永続化し、再起動時は差分だけ取る
- 再走査は**明示的なエンドポイント**（+ 任意の定期実行）。**`inotify` は使わない** — SMB 越しでは
  ファイル変更通知が信頼できない

再走査は `POST /api/rescan`, SIGHUP (`systemctl reload`), `--rescan-interval` の定期実行の3つから起こす。マニフェストも読み直すので、部屋を足すのに再起動は要らない。起動時と同じ `load()` を通し、結果は丸ごと新しいスナップショットにして差し替える。読み込みに失敗したら前のスナップショットで配信を続け、エラーの詳細はログにだけ出す (パスを含むため)。リクエストは最初に取ったスナップショットだけを使うので、2回の走査の結果が混ざることはない。
- 寸法取得はヘッダのみ読む（`into_dimensions()` 相当）。全デコードすると走査時間が桁で変わる

索引をメモリに持つ規模感: 1 画像あたり概ね 150 バイト程度なので、10 万枚で約 15 MB、100 万枚で約 150 MB。
PoC の規模では問題にならない。限界に当たったら SQLite に落とすのが逃げ道。

**実測（段階2、ローカル SSD、`ss/` 368枚）**: 走査 145 ms、**0.5〜1.2 ms/枚**。形式による差はほぼ無く、
240 MiB の PNG 28枚が 27 ms なので `into_dimensions()` がピクセルをデコードしていないことは確認済み
（`image` の JPEG 読み取りは SOF0 の先まで走るが、エントロピー符号部はデコードしない）。

ただし **CIFS ではこの数字が一切参考にならない**。1 枚あたりの操作が
`canonicalize`（パス解決）→ `open` → ヘッダ read → `stat` と最低 4 往復あり、
往復 20 ms なら 368 枚で 30 秒規模になる。段階7 で手を打つ対象は 2 つ:

- 走査結果の永続化（起動ごとの再走査をなくす）
- **走査の並列化**。レイテンシ律速なので、並列度を上げるだけで素直に縮む（CPU 律速ではない）
- 併せて、1 枚ごとの `canonicalize` を見直す余地がある（現状は封じ込め invariant のために毎回呼んでいる）

### 6.3 並び順

自然順ソート（`img2` が `img10` より前）を既定にする。辞書順だと写真の並びが崩れる。`natord` 等。
`order: name | mtime | taken` をマニフェストで部屋ごとに指定できるようにする。

`taken` は撮影日時の順。当初の案では `exif_date` と呼んでいたが、動画は EXIF ではなく `mvhd` の作成日時を使うので、名前を中身に合わせた。

- 写真は EXIF の `DateTimeOriginal` (なければ `DateTimeDigitized`) を読む。EXIF の時刻はカメラの時計の読みで、タイムゾーンは別のタグ (`OffsetTimeOriginal`) にある。iPhone はこれを書くので、それを使って UTC にそろえる。書かないカメラの時刻は UTC とみなす。同じカメラの写真どうしの順は崩れないが、動画と混ざると時差の分だけずれうる
- 動画は `mvhd` の作成日時 (1904年起点の UTC) を使う
- 撮影日時のないファイルは更新日時で代わりに並べる。同じ時刻のものは名前の自然順で並べる。連写は同じ秒に収まるため

### 6.4 パス安全性

API がパスを受け取らない設計（5 章）で攻撃面は消えるが、マニフェストの `path` は依然ユーザー入力。

- 起動時にルートを `canonicalize` する
- 解決したパスはすべて `canonicalize` 後にルート配下であることを検証する
- **パス解決の関数を 1 つに集約し、ファイルシステムに触るコードはそこだけを通す**

### 6.5 フロントの壁の実装

- 壁は flex で `[左の扉群][帯][右の扉群]`。帯を独立させることで、
  扉の位置が画像の流れ方に左右されない
- 段ごとに横の帯を1本ずつ縦に積む。どの帯に入れるかは JS が決める (下の「詰め方の変更」)。帯の数が段数と同じなので、縦のオーバーフローは原理的に起きない
- コンテナ: `overflow-x: auto; overflow-y: hidden`。端で止まるのは既定の挙動そのまま
- scroll-snap は**使わない**（「ただスクロールするだけ」の要件に沿う）。自由スクロールのほうが単純で速い
- 各画像は高さ固定・幅 = 高さ × アスペクト比（API の `w`/`h` から算出）。ピクセル到着前にレイアウト確定
- `<img loading="lazy" decoding="async" srcset="…320w, …640w, …1280w" sizes="…">`。
  遅延読み込みと解像度選択はブラウザに任せる（Slint の canvas 方式を採らなかった理由がここ）
- ルーティングは `/room/{id}` の実パス。axum 側で SPA フォールバックを張る

#### 段数の決め方（実測つき）

段高は通常ビューポート高さから決まるが、**幅でも上限を掛ける必要がある**。16:9 の画像は幅が高さの約1.78倍なので、
高さだけで決めるとスマホでは画像が画面幅を超えて1枚も収まらない（実測: 390px 幅で画像が405px 幅になった）。
よって `--tier-height: min(高さ由来, 40vw)`。この `40vw` は狭い画面でしか効かない。
さらに狭い画面では段高が下がって壁が余るので、段数を増やして埋める。

| ビューポート | 段数 | 段高 | 選択 rendition | 転送量 | 可視枚数 |
|---|---|---|---|---|---|
| 2560x1440 | 4 | 293px | 640×31, 320×1 | **0.63 MiB** | 16 枚 |
| 1920x1080 | 4 | 218px | 640×31, 320×1 | **0.63 MiB** | 12 枚 |
| 1536x864 | 3 | 234px | 640×31, 320×1 | **0.63 MiB** | 6 枚 |
| 390x844 dpr2 | 4 | 156px | 640×31, 320×1 | **0.63 MiB** | 4 枚 |
| 844x390 dpr2 | 2 | 158px | 640×31, 320×1 | **0.63 MiB** | 4 枚 |

（同じ壁が 1 段のときは 2.98 MiB、サムネイル導入前は 82 MiB だった）

#### 列の不揃いという限界

列幅は `max-content`、つまりその列で最も幅広い画像に合わせる。アスペクト比が揃っていれば問題にならないが、
混在すると縦長画像がパノラマと同じ列に入ったときに大きな隙間ができる。実測した列の充填率:

| 素材 | 充填率 |
|---|---|
| `ss/myst`（16:9 が大半） | **98%** |
| アスペクト比を意図的に混在させた検証用画像 | **59%** |

スクリーンショットの素材では問題にならないので、段階4まではそのままにしていた。

#### 詰め方の変更（段階6）

本番の対象は縦長を多く含む写真と PDF（A4 縦が多い）なので、59% の側が常態になる。段階6で詰め方を変える。

- 段グリッドをやめ、**段ごとに独立した横の帯**にする。各作品は段高固定・幅 = 段高 × アスペクト比
- 各作品を**その時点で最も短い帯**に順に入れる。寸法は API が返しているので、ピクセル到着前に JS で配置が決まる
- 隙間は右端の不揃いだけになる。スクロールは横方向のみのままで、扉・位置の復元・キーボード、
  段高からの rendition 選択はそのまま成立する

**代償は並び順。** 「上から下、それから右」という厳密な順序はなくなり、「おおむね左から右」になる。
撮影順に厳密に追いたい場面では気になる可能性があるので、実物で見て判断する。

縦長を 2 段ぶち抜きにする案は採らない。幅が揃わず隙間が残るうえ、埋めようとすると順序が大きく崩れる。

実装 (2026-11-23): `Wall.tsx` の `pack` が、各作品の描画幅に隙間を足した長さで帯の長さを数え、最も短い帯に入れる。同じ長さなら上の帯を選ぶので、作品の少ない部屋は上から埋まる。段数、段高、隙間は `useTierLayout` が CSS から測る。ライトボックスの前後の移動は、壁の見た目の順ではなく部屋の並び順のまま。

縦横混在の検証用画像で測った充填率 (右端の不揃いを含む):

| 段数 | 列のグリッド (旧) | 最も短い帯 (新) |
|---|---|---|
| 2 | 71% | 100% |
| 3 | 64% | 91% |
| 4 | 59% | 81% |

### 6.6 画像以外の種別 — HEIC・動画・PDF（段階5）

やることは種別によらず同じ 2 つ: **壁にサムネイルを掛ける**ことと、**選んだら本体を閲覧できる**こと。
どの種別も「1 枚の絵にしてしまえば、あとは画像と同じ経路」に乗せる。4 サイズの WebP、ディスクキャッシュ、
single-flight、セマフォ（§6.1）は変えない。種別ごとに違うのは、寸法の取り方、絵の作り方、開いたときの見せ方だけ。

| 種別 | 寸法（走査） | サムネイルの元になる絵 | 開いたとき |
|---|---|---|---|
| 画像（HEIC 含む） | ヘッダ | デコードした画像 | 2560 の WebP |
| 動画 | `ffprobe` | `ffmpeg` で取り出した 1 コマ | `<video controls>` に `orig` |
| PDF | 1 ページ目の寸法 | 1 ページ目のラスタライズ | ブラウザ内蔵のビューアで `orig` |

動画は、上の表の計画から2点を変えた (2026-11-23)。寸法、回転、長さは `ffprobe` ではなく、`museum_core::video` が MP4/MOV の `moov` を直接読んで得る。子プロセスも実行時の依存も要らず、`mdat` を読み飛ばすので走査はヘッダー読みのまま済む。壁のコマはサーバーで作らず、ブラウザーが `<video preload="metadata">` とメディアフラグメント `#t=0.1` で `orig` から描く。サムネイル API は動画に 404 を返し、見取り図の表紙と扉の `peek` には静止画だけを選ぶ。動画が増えて壁の読み込みが重くなったら、`ffmpeg` による1コマのサムネイルを計画どおり足す。対応する容器は MP4/MOV だけで、WebM は掛からない。スライドショーは動画を飛ばす。

`orig` は `ServeFile` が Range に応えるので（`CLAUDE.md`）、動画のシークも PDF の部分読み込みも
サーバ側の追加なしで成立する。

**採用予定の依存（未検証）**

- HEIC: `libheif-rs`（`libheif` のバインディング）。配布元のパッケージが古いとビルドが通らないことがある
- PDF: `pdfium-render`。MuPDF は AGPL なので避ける。poppler の `pdftoppm` を子プロセスで呼ぶ手は簡単だが遅い
- 動画: `ffprobe` / `ffmpeg` を**子プロセス**で呼ぶ。Rust から直接リンクするクレートはビルドが重い

いずれも実行時に外部のライブラリか実行ファイルを要するので、「単一バイナリを置くだけ」ではなくなる。
見つからないときは起動時にその種別を無効にして警告し、サーバ全体は落とさない。

**落とし穴**

1. **HEIC の向きを二重に直さない。** HEIC は回転をコンテナ側に持ち、`libheif` がデコード時に適用する。
   そこへ EXIF Orientation の補正（§6.1）を重ねると二重に回る。HEIC だけは EXIF 補正を外す。
2. **動画の寸法は回転を見て入れ替える。** スマホの縦撮りは記録上は横長で、回転情報が別に付く。
   `ffprobe` の寸法をそのまま返すと壁が誤った形に組まれる。段階2で EXIF について踏んだのと同じ誤り。
3. **ライトボックスは原寸を出さない。** HEIC は Safari 以外で表示できない。画像は全形式で 2560 の WebP を既定にする。
   カメラの JPEG は 1 枚が数 MB から十数 MB あるので、転送量の面でもこのほうがよい。
4. **Live Photos の対を壁に掛けない。** 写真と同じ名前の `.MOV` は対になる動画で、独立した作品ではない。
5. **走査が重くなる。** 動画は 1 本ごとに子プロセスを起動し、PDF の寸法は末尾の相互参照表から辿るので
   ヘッダだけでは済まない。CIFS では往復が増える。走査結果の永続化（§6.2）が前提になる。
6. **壁の上では再生しない。** 自動再生もホバー再生もしない。動画には再生マークと長さを重ねて写真と見分ける。

**範囲に入れないもの: トランスコード。** 動画は元ファイルをそのまま再生する。H.264 の MP4 はどこでも再生できるが、
HEVC はブラウザと端末しだい。再生できない動画が実際に多いと分かったときだけ H.264 への変換を足す。
CPU を長時間使い、変換結果の保存容量が要り、サムネイルとは別の待ち行列が必要になる重い部品なので、
実ライブラリのコーデックの内訳を見てから判断する（`.local/status.md`）。

PDF も同じ考え方で、まずブラウザ内蔵のビューアに任せる。インライン表示できない環境が問題になったら pdf.js を同梱する。

### 6.7 ネットワークとアップロード経路

**構成**: 家庭用の Wi-Fi ルーター 1 台。サーバ（NixOS）は有線、スマホは無線で同じ LAN に入る。
ルーターはインターネット接続を兼ねるが、ポート開放はしないので外からは届かない。

- サーバのアドレスはルーターの DHCP 固定割り当てで固定する。加えて Avahi（mDNS）で `名前.local` でも引けるようにする。
  Android は `.local` を引けないことがあるので、フォトフレーム用の端末は IP アドレスで指定する
- スマホはゲスト Wi-Fi に繋がない。ルーターのプライバシーセパレーター（AP 隔離）は無効にする
- NixOS のファイアウォールで lumier と Samba のポートを開け、lumier は `--bind` で LAN 側に出す
- 外出先から使いたくなったら Tailscale を足す。lumier 側の変更はバインド先が増えるだけ

**認証**: 閲覧だけで LAN（と Tailscale）の内側に限るあいだは、認証なしで始める。
フォトフレーム用の端末はログイン操作を挟みにくいので、「ネットワークの内側は信頼する」方針と相性がよい。
lumier に書き込み経路を作る時点で必要になる。段階9の削除予定は、serve がライブラリに書き込まない形にしたので、認証なしのまま進める (§6.9)。

**アップロード**: 取り込みと閲覧を分ける。**lumier は読むだけのまま**にし、スマホからは SMB で直接書き込む。
要件は「選んだものを、振り分け先のフォルダを決めて送る」で、自動の一括バックアップではない。

1. まず iOS の「ファイル」アプリから SMB に保存する。作るものがない
2. 大量転送で不安定なら PhotoSync などの転送アプリに切り替える。Android でも同じ形が使える
3. それでも面倒なら lumier にアップロード機能を作る（§8）

送ったあと壁に反映するには再走査が要る。新しいフォルダを部屋にするにはマニフェストの編集が要る。

lumier のアップロードを後回しにする理由は 2 つ。iOS のブラウザは写真ライブラリから選んだ HEIC を JPEG に変換し、
動画を再圧縮することがあり、元ファイルの保管には致命的（未確認、作る前に実機で確かめる）。
そして共有に書き込まないという性質がなくなる。作る場合は送り先を部屋 ID で指定し、
「API はパスを受け取らない」（§5）を保つ。

### 6.8 Markdown とリンクの解決（段階8）

Obsidian で書いたノートを、**素の Markdown として**壁に掛けて読めるようにする。Obsidian の保管庫ビューアは作らない。
想定は「写真や PDF に添える説明や記録のノート」で、リンクの相手は主に PDF や画像などの添付ファイル。
ノート同士が大量にリンクし合う保管庫を読む用途は対象外（§8）。

**種別を 1 つ足すだけ**（§6.6 の仕組みに乗る）。

- 壁: Markdown には絵がないのでサムネイルは作らない。題名（最初の見出し、なければファイル名）と冒頭の数行を
  API で返し、フロントがカードとして描く。大きさは縦長の固定比率
- 開いたとき: サーバ側で HTML に変換した本文をライトボックスの位置に出す。`comrak` か `pulldown-cmark`。
  表やチェックリストなど GitHub 流の記法まで
- 生の HTML が書けるので、変換後に無害化する。冒頭のフロントマターは隠す

**リンクはファイル名で解決する。** ノート内のリンクはパスを指しているが、アップロードした先のフォルダ構成は
保管庫と一致しない。そこでパスからファイル名だけを取り出し、走査で作った索引を名前で引いて、ID の URL に書き換える。
Obsidian 自身も位置ではなく名前で相手を探すので、同じ考え方になる。

- 対象の書き方: `[文字](path/資料.pdf)`、`[[資料.pdf]]`、`![[写真.png]]`、`![](写真.png)`
- 置き場所は自由。リンク先はどの部屋のフォルダにあってもよく、アップロードの順番も問わない。
  後から足したファイルは次の再走査でつながる
- 解決はサーバの中で行い、ブラウザに渡るのは ID だけ。「API はパスを受け取らない」（§5）を保つ。
  **変換をサーバ側に置く理由はこれ**
- `#page=3` のようなページ指定は URL にそのまま残す。ブラウザの PDF ビューアがそのページで開く

**決めた規則**

1. **同名のファイルが複数あるとき**: 同じ部屋のものを優先。なければ、ライブラリ全体で 1 つだけのときに採用。
   それ以外は未解決にする（黙って片方を選ばない）
2. **名前は正規化してから比べる。** iOS や macOS から送ったファイルは濁点付きの文字の内部表現（NFD）が違い、
   見た目が同じでも一致しない。NFC に揃え、大文字小文字は無視し、`%20` などの URL エンコードは戻す
3. **索引に入るのは、マニフェストで部屋として掛けたフォルダの中だけ。** リンク先はどこかの部屋に入っている必要がある
4. **切れたリンクは見えるようにする。** 表示では色を変えて示し、`lumier check` は未解決と同名重複の一覧を警告として出す。
   「リンク先もアップロードする必要がある」という手間は残るので、足りないファイルにすぐ気づけることで補う

**対応しないもの**: コールアウト、Dataview などプラグイン由来の記法、ノートの埋め込み（`![[別のノート]]`）。
そのまま文字として表示する。

**前提**: 段階5（種別）と段階7（再走査）。再走査がないと、後から足したリンク先がつながらない。

### 6.9 削除の予約と trash (段階9)

一括でアップロードしたものを壁で見ながら、いらないものに印を付ける。目的は選別なので、その場で消す必要はない。そこで serve は印を記録するだけにし、ファイルを動かすのは夜間のバッチに任せる。

#### 流れ

1. 削除予定: 壁かライトボックスで印を付ける。serve は状態ファイルに記録するだけで、ライブラリには触らない
2. trash: 毎晩のバッチが削除予定のファイルを trash に移す
3. 消去: trash に移してから30日経ったものを、バッチが消す

どの段階でも取り消せる。削除予定は印を外せばよい。trash にあるものは復元を予約すると、次のバッチで元の場所に戻る。

serve はライブラリに書き込まない。印の付け外しも復元の予約も、serve が書くのは状態ディレクトリの中だけ。ファイルを動かす権限はバッチにだけ持たせ、NixOS ではユニットを分ける。serve にはライブラリと trash を読み取り専用で渡す。こうすると §6.7 の「lumier は読むだけ」が serve については保たれ、serve に穴があってもファイルは消えない。

#### 状態ファイル

`{state-dir}/marks.json` に削除予定を、`{state-dir}/restores.json` に復元予定を持つ。削除予定の各項目は、ルート相対パス, `v`, 登録日時の組。相対パスはサーバーの中のファイルに残るだけで、クライアントには渡らない。

`v` を残すのは、印を付けたあとで同じ名前のファイルが差し替えられた場合に備えるため。バッチは今のファイルの `v` が記録と違えば移さず、項目を捨ててログに残す。印を付けたのとは別のファイルを消す事故は、これで防げる。ファイルがもう無いとき (SMB から直接消したなど) も項目を捨てる。

状態ディレクトリの `.lock` に `File::lock` をかけて、serve とバッチの競合を防ぐ。serve は印を変えるたびに、排他ロックの下でファイルを読み直し、変更を加え、`.part` に書いて rename で置き換える。バッチは実行中ずっと排他ロックを持つので、そのあいだに付けた印はバッチを待ってから記録され、バッチの書き戻しで消えることはない。serve は最後に読み書きした状態をメモリに持ち、再走査のときに読み直す。可変なのはこの状態だけなので、`AppState` 全体ではなくこれだけを `Mutex` で包む。

#### trash の構造

`{trash}/{移した日付}/{ルート相対パス}` に置く。例: `trash/2026-11-24/2026/旅行/IMG_0021.jpg`

- 元の階層を残すので、復元は逆向きの rename 1回で済む。手で `mv` しても戻せる
- 経過日数は日付ディレクトリの名前で判断する。systemd-tmpfiles の経過日数による削除は使えない。rename では mtime が変わらず、古い写真は移した当日に消されてしまう
- 日付は UTC で数える。並べて引き算できれば足り、タイムゾーンのデータベースを持ち込むほどではない。毎晩4時 (日本時間) のバッチなら、ディレクトリ名は前日の日付になる
- 復元で空になったディレクトリは、日付ディレクトリまで遡って消す
- trash はライブラリと同じファイルシステムに置き、rename を原子的にする。置き場所はライブラリのルートの外にして、走査の対象にしない
- Live Photo の対の動画 (§6.6) は、静止画と一緒に移して一緒に戻す
- serve は起動時に trash も走査する (読むだけ)。一覧の表示とサムネイルに使う

#### バッチ (`lumier purge`)

systemd timer で毎晩4時に動かす。順番は次のとおり。

1. 状態ディレクトリの排他ロックを取る
2. 復元予定を元の場所に戻す。戻す先に同じ名前のファイルがあれば上書きせず、trash に残してログに出す
3. 削除予定を trash に移す
4. 30日を過ぎた日付ディレクトリを消す
5. 状態ファイルを書き戻してロックを放す
6. serve に再走査させる (`systemctl reload lumier`)

当初は、状態ファイルの競合を避け、移したファイルを壁から外すために、バッチの前後で serve を止める案だった。ロック (上の「状態ファイル」) と再走査 (段階7) で両方が済むようになったので、serve は止めない。

バッチは起動時に、trash とライブラリが同じファイルシステムにあることを確かめ、違えば何もせずに終わる。別のファイルシステムでは rename が使えず、コピーと削除になって途中で失敗しうるため。NixOS のユニットでは `ProtectSystem = "strict"` と `ReadWritePaths` を組み合わせない。パスごとに別のバインドマウントになり、同じファイルシステムでも rename が EXDEV で失敗するため。

日数は `--trash-days` で、時刻は timer の設定で変えられる。

一晩で移す数に上限を置く。serve には認証がないので、LAN の内側からなら誰でも印を付けられる。全部に印を付けられても、バッチは上限 (既定500件) を超えたら何も移さずに止まり、ログに出す。本当にまとめて消したいときは `lumier purge --no-limit` を手で走らせる。30日の猶予と合わせて、気づかないうちに全部が消える事態を防ぐ。

#### 表示と操作

- 壁: 削除予定の絵は白黒にして薄くし、右下に赤いゴミ箱のアイコンだけを、背景なしで置く。丸い ✕ や、背景の付いたラベルは使わない。ボタンのように枠のあるものは、押すと印が外れるように見えてしまう。部屋の表紙には削除予定でない絵を選ぶ。スライドショーでは飛ばす
- 印の付け外し: ライトボックスのボタンか `D` で切り替える。壁には選択モードを置き、そのあいだはタップで印を切り替える。取り消せる操作なので確認は挟まない
- 削除予定の一覧: 館内マップから入る特別な壁。全部の部屋の削除予定を、マニフェストの部屋の順に並べて掛ける。どの部屋のものかはライトボックスの説明と、壁のツールチップに出す。ここで印を外しても壁から消えず、もう一度付け直せる
- trash の一覧: 同じく館内マップから入る特別な壁。新しい日付から並べ、移した日付と消去までの残り日数をライトボックスの説明に出す。ここで復元を予約でき、予約したものは目印を変えて示す。選択モードとライトボックスのボタンは、ここでは復元の予約を切り替える

特別な壁はマニフェストの部屋ではなく、扉も持たない。描画には壁の部品をそのまま使う。クライアントでの ID は `~marks` と `~trash` で、ルーム ID に使える文字 (英小文字, 数字, `_`, `-`) に `~` は含まれないので衝突しない。スライドショーは特別な壁からは始めない。

#### API

```
PUT    /api/marks/{image_id}            削除予定に登録する
DELETE /api/marks/{image_id}            削除予定から外す
GET    /api/marks                       削除予定の一覧。部屋ごとにまとめる
GET    /api/trash                       trash の一覧。日付ごとにまとめ、残り日数と復元予定かどうかを付ける
PUT    /api/trash/{trash_id}/restore    復元を予約する
DELETE /api/trash/{trash_id}/restore    復元の予約を取り消す
```

部屋 API の各要素には `marked` を足す。削除予定の一覧の要素には部屋の名前 (`room`) を、trash の一覧の要素には `day`, `days_left`, `restore` を足す。どれも、何度送っても結果が同じになる形にしている。`GET /api/museum` は `marking` を返し、フロントはこれを見て印の操作を出すか決める。

trash の中のファイルも ID で指す。ID は trash のルートからの相対パスに `trash:` を前置して blake3 にかけ、ライブラリの ID と衝突させない。解決は `path::resolve` に trash のルートを渡して行う。これで「API はパスを受け取らない」(§5) と「パス解決は1か所」(§6.4) はどちらも保たれる。サムネイルはライブラリと同じく `/img/{id}/{size}` で出す。

#### CSRF と有効化

認証はないが、手元のブラウザーで開いた別のサイトから印を付けられるのは防ぐ。書き換えは `PUT` と `DELETE` だけなので、別オリジンからのリクエストは preflight で止まる。加えて、`Origin` が自分でなければ拒否する。

`--state-dir` と `--trash-dir` を両方渡したときだけ有効にする。渡さなければ今までどおり閲覧専用で、フロントも印の操作を出さない。

#### 前提

段階7の NixOS のサービス化と再走査。`nix/module.nix` の `services.lumier.marking` で、serve の引数、状態ディレクトリ、バッチのユニットと timer をまとめて有効にする。ローカルでは `lumier purge` を手で走らせれば一通り試せる。

## 7. PoC の段階計画

ローカルの普通のディレクトリを相手に、各段階が単体でデモできる形で積む。

|---|---|---|
| **0. 骨組み** | cargo workspace + Vite、部屋 1 つ決め打ち、原寸をそのまま配信 | ブラウザでローカルフォルダの画像が横一列に並び、スクロールできる |
| **1. マニフェストとグラフ** | `museum.yaml` の解析・検証、`lumier check`、複数部屋、左右の扉、スポーン規則 | 壊れたマニフェストが起動時に落ちる。扉で部屋を往復でき、進行方向が保たれる |
| **2. 走査と寸法** | 走査器、`w`/`h` つき API、自然順ソート | 読み込み中にスクロール位置が飛ばない（段階 0 との差が体感できる） |

| **5. 形式の拡張** | 種別（画像/動画/PDF）、HEIC、動画 1 コマと PDF 1 ページ目のサムネイル、種別ごとのライトボックス | HEIC・動画・PDF が混ざったフォルダが壁に並び、それぞれ開いて見られる。横倒しがない |
| **6. 壁の詰め直しと並び順** | 最も短い段に入れる詰め方、`order: taken` | 縦横混在のフォルダで隙間が右端の不揃いだけになる。撮影順に並ぶ |
| **7. サーバへの配置** | 走査結果の永続化、再走査、NixOS のサービス化、LAN への公開 | サーバ上の実ライブラリを、スマホから LAN 越しに実用速度で見られる。写真を足したら再起動なしで壁に出る |
| **8. Markdown** | Markdown の種別、カード表示、HTML への変換、ファイル名によるリンクの解決（§6.8） | ノートが壁に掛かり、開いて読める。別の部屋に置いた PDF へのリンクがつながる。切れたリンクが `check` で分かる |
| 9. 削除の予約 | 削除予定の印、`lumier purge` による trash への移動と30日後の消去、削除予定と trash の一覧と取り消し (§6.9) | 壁で印を付けた絵が翌朝には壁から消え、trash の一覧から戻せる。serve はライブラリに書き込まない |

段階5〜7は 2026-10-11 の組み直し。当初は「5. NAS 対応」だけだったが、本番の対象が
スクリーンショットではなく写真・動画・PDF だと分かったので、形式と詰め方を先に入れた。
どちらも NAS なしでローカルで進められ、段階5で走査が重くなることが段階7の設計に効くので、この順にしている。
